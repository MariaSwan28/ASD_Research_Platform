# Подключение модели через адаптер

Платформа использует один контракт результата 1.2 и одну карточку React. Различия между моделями реализуются внутри адаптера: подготовка входа, вызов модели, расшифровка классов, тексты вывода, показатели и подробные таблицы.

Существующие частные реализации:
- `core/ml_adapters/parent_story.py` — CountVectorizer + Naive Bayes, расшифровка 0/1, текущий режим целого рассказа.
- `core/ml_adapters/movement_video.py` — извлечение движений, показатели обработки и таблица по частям тела. Итоговая классификация пока не подключена.

## Шаблон

Скопируйте `adapter_template.py` в `core/ml_adapters/<имя_адаптера>.py`. Исходный шаблон находится вне каталога обнаружения и не появляется у пользователей как готовая модель.

1. Заполните MODEL: уникальный id, label, version, modality, input_types, extensions, operation и result_schema_version='1.2'.
2. Реализуйте infer(payload): исходную предобработку и предсказание. Для текста доступен payload['text']; для файлов — путь payload['file_path'], сформированный сервером после проверки владельца. Не загружайте модели из пользовательских файлов и не обучайте их на каждом запуске.
3. Реализуйте status(): проверку зависимостей и доверенных артефактов. Только затем включите IMPLEMENTED. Не запускайте инференс при проверке готовности.
4. Настройте present(raw): соответствие классов, понятный заголовок и объяснение, основные показатели с единицами, ограничения. Для неизвестной метки нужен отдельный результат, а не отрицательный класс по умолчанию.
5. Подготовьте контрольные примеры с известным исходным результатом. Проверьте успешный запуск, недоступную модель, неподходящий материал, неизвестный класс и сохранение неизвестных дополнительных полей.
6. Пересоберите ML-сервис. Для поддержанного пути загрузки новая модель обнаруживается автоматически; React и общие маршруты Node.js менять не требуется. Если новый формат ещё нельзя загрузить, его поддержку хранения нужно добавить отдельно.

## Обязательные поля модели и запуска

MODEL определяет способ выбора модели. Результат analyze(payload) строится функцией make_result().

| Аргумент make_result | Требование |
|---|---|
| conclusion | Обязательный объект: code, title, explanation — непустые строки |
| metrics | Обязательный массив скалярных показателей; может быть пустым |
| limitations | Обязательный массив строк; может быть пустым |
| raw_output | Обязательный полный JSON-совместимый исходный результат |
| parameters | Необязательное типизированное представление подробностей; по умолчанию формируется из raw_output |
| artifacts | Необязательный массив зарегистрированных файлов; по умолчанию [] |
| warnings | Необязательные предупреждения совместимого контракта; по умолчанию [] |
| summary | Необязательная краткая строка; по умолчанию conclusion.title |

Каждый основной показатель: key, label, type, value, description; unit при необходимости. Поддержанные типы основных показателей: string, number, integer, boolean. Для отсутствующего значения задайте value=null и известный тип явно (например, parameter(..., type='number')). Не заменяйте отсутствие данных нулём.

Модельные массивы, вложенные объекты и таблицы размещайте в parameters. parameter(..., type='table', columns=[...]) позволяет сделать частный подробный отчёт без нового компонента React. Исходный raw_output сохраняйте полностью, даже если некоторые поля не входят в основные показатели.

Общий исполнитель формирует schema_version, analysis_id, status, model, input, execution, error. Адаптер не должен придумывать идентификаторы или помечать неудачный запуск успешным. Для ожидаемой ошибки используйте AdapterError(code, message, http_status), без внутренних путей и трассировки в публичном сообщении.

Полный перечень полей итогового API-ответа приведён в `STAGE13_UNIFIED_RESULTS.md` в корне проекта. Обязательная структура проверяется Python и Node.js перед сохранением. Старые результаты 1.0 доступны для чтения.

## Семантика частных моделей

- Уверенность классификации, доля предложений и качество трекинга — разные величины. Подпись должна объяснять именно вычисленное значение.
- Для текстового адаптера значение 0/1 взято из диплома Лебедевой, с.33. Это документированная схема разметки; соответствие конкретных pickle данному варианту обучения ещё нуждается в контрольной проверке. Предобработка по предложениям пока не восстановлена.
- Для видео нельзя выводить итоговый класс вместо результата отсутствующего или упавшего классификатора. Предварительная аннотация по правилам остаётся отдельным исходным показателем.
- Модель не определяет медицинский диагноз ребёнка. Класс относится к анализируемому материалу и обучающей разметке.

## Проверки

Из каталога ml-service:

```bash
python -m unittest discover -s tests -p 'test_*.py' -v
```

test_adapter_template.py проверяет инертность шаблона, выполнение через общий исполнитель с заглушкой модели, обязательные поля, неизвестные классы и таблицы. Эти тесты не подтверждают качество настоящего инференса. После реализации адаптера нужны отдельные примеры из его исходного окружения.

## Тексты для пользователя

conclusion.title — короткий итог, explanation — одно предложение. В metrics оставляйте только полезные пользователю значения; внутренние числа и подробные таблицы — в parameters. Не включайте переписку, ссылки на дипломы, имена авторов, TODO, pickle, названия библиотек и историю разработки в вывод и ограничения. Эти сведения относятся к документации разработчика. Предупреждение «Результат анализа не является диагнозом» показывает общий интерфейс один раз; не дублируйте его в warnings. Пояснения основных показателей доступны по наведению.

Этап 15: исполнитель возвращает формат 1.2. Добавлен статус partial: характеристики получены, но один из шагов не завершён. error содержит причину, а parameters и artifacts сохраняют успешные результаты. Форматы 1.0 и 1.1 продолжают читаться; новые адаптеры используют 1.2.
