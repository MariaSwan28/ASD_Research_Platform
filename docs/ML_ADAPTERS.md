# Подключение ML-моделей: контракт 1.0

## Назначение

Модель выполняет свой алгоритм. Адаптер проверяет вход, воспроизводит предобработку,
вызывает алгоритм и описывает его выход. Общий Python-слой добавляет сведения о запуске.
BFF проверяет права, проверяет ответ, сохраняет JSON в SQLite. React отображает параметры
по описанию, без условий по ID модели.

Новых сервисов, очередей и таблиц не добавлено. Используется существующая таблица
`UnifiedAnalysisResults`. Исходные таблицы результатов остаются доступными.

## Что подготовить для новой модели

1. Уникальный стабильный ID, название, назначение и версию. Версия меняется при изменении
   весов, словаря, предобработки или значимой логики. `schema_version` — отдельно версия JSON.
2. Поддерживаемые расширения и MIME-типы, модальность и операцию.
3. Обученные артефакты и их происхождение, совместимые зависимости, точную предобработку.
   Если алгоритм не требует обучения, артефакты не обязательны.
4. Контрольный материал и ожидаемый результат или проверяемые свойства результата.
5. Доверенный Python-модуль в `ml-service/core/ml_adapters/`.

Не размещать зависимости с тяжёлой инициализацией на верхнем уровне модуля. Импорт реестра
не должен загружать веса. Модуль адаптера — код разработчика, не пользовательский файл.
Не добавлять демонстрационные адаптеры в этот каталог как доступные реальные модели.

## Интерфейс модуля

```python
MODEL = {
    "id": "my-model-v1",
    "version": "1.0",
    "label": "Название модели",
    "modality": "image",
    "operation": "image-analysis",
    "extensions": [".png", ".jpg"],
    "input_types": ["image/png", "image/jpeg"],
    "result_schema_version": "1.0",
}

def status():
    # Проверить наличие реальных артефактов/зависимостей.
    return "unavailable", "trained_artifact_not_installed"

def analyze(payload):
    from core.result_contract import AdapterError
    # Здесь должны быть реальная проверка входа, предобработка и инференс.
    raise AdapterError("model_unavailable", "Модель не установлена", 503)
```

Это шаблон интерфейса, не рабочая модель. Когда реальные результаты получены,
`analyze()` возвращает ровно четыре поля:

```python
from core.result_contract import parameter

# measured_value должен быть вычислен настоящим алгоритмом.
return {
    "summary": "Обработка завершена",
    "parameters": [parameter("metric", measured_value, "Измеренный показатель", unit="ед.")],
    "artifacts": [],
    "warnings": [],
}
```

Адаптер не импортирует Flask, не читает `request`, не возвращает `Response` или HTTP-кортеж.
`status()` возвращает `("configured", None)` либо `("unavailable", "код причины")`.
`configured` означает техническую конфигурацию, а не проверенную точность модели.
Сбой проверки статуса делает модель недоступной; ошибка импорта адаптера записывается в
лог, при этом остальные импортируемые адаптеры продолжают работать. Ошибки описания модели
(включая повторяющиеся ID) требуют исправления разработчиком, а не молчаливого выбора модели.

## Вход

Публичный запрос остаётся прежним:

```json
{ "fileId": "UUID сохранённого материала", "modelId": "my-model-v1" }
```

BFF находит файл **по ID и владельцу**, определяет совместимость и самостоятельно
формирует поля для адаптера:

| Поле | Содержание |
| --- | --- |
| `analysis_id` | UUID запуска, созданный BFF |
| `file_id` | ID сохранённого материала |
| `user_id` | ID авторизованного пользователя |
| `file_path` | Проверенный серверный путь к материалу в общем томе |
| `file_name` | Имя материала |
| `text` | Для текстовой модальности: содержимое TXT, до 20000 символов |
| `video_path` | Для видео: совместимый со старым конвейером псевдоним пути |

Клиентские пути и идентификатор запуска не используются. Для новых файловых модальностей
не нужно добавлять ветку в BFF: адаптер получает общий путь. Для специальных новых способов
ввода (например, поток вместо сохранённого файла) потребуется отдельное расширение контракта.
Поля `file_path`, `video_path`, `user_id` не включаются в общий публичный результат.

Текущий выбор совместимости выполняется по расширению. `input_types` описывает поддержку,
но не подтверждает фактическое содержимое: проверка содержимого — задача адаптера.
Универсальное хранилище MIME/категорий из другого этапа в эту исходную версию не перенесено.

## Итоговый JSON

Все общие поля обязательны:

| Поле | Формирует | Значение |
| --- | --- | --- |
| `schema_version` | Python | `1.0` |
| `analysis_id` | BFF | ID запуска и записи истории |
| `status` | Общий слой | `completed` / `failed` |
| `model` | Реестр | `id`, `name`, `version`, `modality`, `operation` |
| `input` | BFF + Python | `file_id`, `modality` |
| `execution` | Python | `started_at`, `finished_at` в UTC, `duration_ms` |
| `summary` | Адаптер / обработчик ошибки | Краткий итог |
| `parameters` | Адаптер | Все частные показатели |
| `artifacts` | Адаптер | Метаданные выходных файлов, пока может быть `[]` |
| `warnings` | Адаптер | Массив пояснений и ограничений |
| `error` | Общий слой | `null` либо `{ "code": "...", "message": "..." }` |

При прямом внутреннем вызове Python без `analysis_id` генерируется UUID,
без `file_id` используется `null`. Публичный BFF всегда передаёт оба идентификатора.
Время Python описывает выполнение вызова адаптера, а не передачу файла и запись в SQLite.
При сетевой ошибке BFF формирует результат ошибки и измеряет время ожидания самостоятельно.

Внешний ответ дополнительно содержит прежние `analysisId`, `fileId`, `childProfileId`,
`model_id`, `model_version` для совместимости. В SQLite сохраняется канонический JSON;
скачивание из истории возвращает его без этих псевдонимов. Семантика основных полей одинакова.

## Параметры модели

Каждый элемент `parameters` содержит:

```json
{
  "key": "features_nonzero",
  "label": "Распознанных признаков текста",
  "type": "integer",
  "value": 12,
  "description": "Количество ненулевых признаков после векторизации"
}
```

`key`, `label`, `type`, `value` обязательны. `unit` и `description` — необязательные строки.
Число в примере условное. Ключи на каждом уровне уникальны и стабильны.

| Тип | `value` | Отображение |
| --- | --- | --- |
| `string` | Строка | Текст |
| `integer` | Целое число | Число |
| `number` | Конечное число | Число и единица, если задана |
| `boolean` | `true` / `false` | Да / Нет |
| `object` | Объект, где каждое значение — описанный параметр | Вложенные группы |
| `array` | Массив обычных JSON-значений | Список с кнопкой «Показать ещё» |
| `table` | Массив объектов строк; дополнительно `columns` | Таблица |
| `json` или будущий тип | Любое JSON-значение | Универсальное представление / JSON |

`null` разрешён для любого типа и означает «Нет данных». Ноль и `false` сохраняются.
`NaN`, Infinity, дубли ключей и несоответствие типа отклоняются. У объектов ключ дочернего
параметра должен совпадать с его ключом в объекте. Массивы не обрезаются: первые 40 элементов,
затем раскрытие следующих; полный JSON всегда содержит все элементы. Глубокие обычные
JSON-структуры показываются как полный JSON внутри раскрываемой группы.

Пример таблицы:

```json
{
  "key": "segments",
  "label": "Фрагменты",
  "type": "table",
  "columns": [
    { "key": "start", "label": "Начало", "unit": "с" },
    { "key": "label", "label": "Метка" }
  ],
  "value": [ { "start": 0, "label": "Пример" } ]
}
```

Все ключи строк должны быть объявлены в `columns`; неизвестные колонки отклоняются,
чтобы данные не исчезали при отображении. Необязательные ячейки показываются как «Нет данных».

Показатели уверенности, вероятности, класса или риска не обязательны. Добавлять их можно,
только если алгоритм их действительно возвращает. Исходная текстовая метка 0/1 не получает
неподтверждённой медицинской расшифровки. `parameter()` автоматически упаковывает обычные
словари и списки без отбрасывания новых ключей; для понятных подписей автор задаёт свои описания.

`artifacts` сейчас содержит только метаданные: `id`, `label`, `media_type`, необязательный
`file_id` уже сохранённого файла. Внутренние пути и произвольные URL запрещены. Автоматическая
регистрация новых выходных файлов и универсальное скачивание артефактов этим этапом
не реализованы. У двух текущих адаптеров это `[]`; прежние JSON/NPZ/видео-файлы видеоконвейера
продолжают создаваться и обслуживаться существующими механизмами.

## Ошибки и история

- Ошибки входа — HTTP 400 Python (422 через общий BFF), неизвестная модель — 404,
  занятость — 409, недоступность — 503, неверный результат адаптера — 502.
- При `failed` выходные параметры пусты, `error` заполнен. Незавершённый анализ не объявляется
  завершённым. В traceback и внутренние пути пользовательский ответ не превращается.
- BFF сохраняет в истории успехи и ошибки после попытки вызова модели. Ошибки предварительных
  проверок (нет доступа, формат не поддерживается, модель заранее недоступна) не создают запуск.
- Истечение таймаута означает сбой ожидания, а не подтверждённую отмену Python-вычисления.
- Сбой SQLite не выдаётся за успешное сохранение; при нём история может не пополниться.
- Старые записи не переписываются: интерфейс читает и прежний JSON, и контракт 1.0.
  Можно выбрать сохранённый запуск, в том числе если адаптер больше не доступен.
  Текущий API возвращает до 40 последних записей общей истории, как и до этого этапа.

## Видео и текст в этом этапе

`movement-pose-v1` использует `VideoAnalysisService` без Flask request context. Старый
`/api/mv_analyze` и новый маршрут `/api/models/movement-pose-v1/analyze` обращаются к одному
сервису; первый отдаёт прежний JSON, второй — контракт 1.0. Каждый запуск получает новый
экземпляр анализатора, чтобы не переносить статистику предыдущего видео. Сохраняются общий
лимит в один видеоанализ на процесс, прогресс и прежние выходные файлы. Задержка разблокировки
на две секунды больше не нужна: итог остаётся доступен в статусе после завершения.

Извлечение признаков и `/api/predict` (отдельный видеоклассификатор в старом окне) не объединены.
`hasAnalysis` выставляется общим API только после успешной операции `movement-analysis`.
Модель с другой видеооперацией сама по себе не означает наличия прежней видеоаналитики.

`parent-story-nb` упаковывает прежний результат по тем же правилам. Артефакты и вычисление
текстовой модели не менялись. Это не подтверждает предобработку, качество и смысл классов.
Старые текстовые API сохранены с прежними ответами для совместимости.

## Проверка новой модели

1. Проверить `status()` без артефактов и с ними, не загружая веса при импорте модуля.
2. Вызвать `analyze(payload)` напрямую без Flask; проверить предобработку на контрольном примере.
3. Проверить результат через `validate_adapter_result()`; не заменять отсутствующие метрики нулями.
4. Проверить общий API, права на файл, запись истории и ошибку исполнения.
5. Проверить все частные параметры, единицы и полный JSON в интерфейсе.
6. Отдельно зафиксировать настоящий инференс и отдельно — тесты с подменой алгоритма.

## Видимость отчёта (этап 18)

`conclusion` и скалярные `metrics` формируют краткий результат для родителя. Подробные блоки отчёта, `parameters`, `raw_output` и файлы доступны назначенному специалисту. Весь отчёт сохраняется на сервере; ограничение применяется при выдаче, в том числе для старой истории. Родительский ответ помечен `report_view: "brief"` и не является исходным полным ML-результатом. Контракт адаптера 1.3 сохранён.
